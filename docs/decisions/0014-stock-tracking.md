# 0014. 완제품 재고 트래킹 (`/stock`)

- 날짜: 2026-09-06
- 상태: 채택 (인프라 완료, 실제 품목 등록 전)

## 맥락

지금 재고는 냉동실 컨테이너 개수를 세서 화이트보드에 적는 완전 오프라인 방식 — 원격으로 못 보고, 기록이 안 남아 추이 파악도 안 됨. 오너의 실제 목적은 딱 두 가지: (1) 지금 뭘 만들어야 하나(뭐가 부족한가), (2) 2호점 오픈 시 어떤 디저트를 배달해야 하나.

처음엔 "재료 원가"(레시피 단가) 이야기였는데, 대화 중 이게 아니라 **완제품 재고**(마카롱 등 만들어진 것의 통 개수)를 관리하고 싶다는 게 명확해짐 — 별개 기능.

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| 매번 정확한 개수 전수조사 + Square 완전 연동 | 가장 정확 | 세는 시간이 오래 걸림 — 정작 오너가 필요한 건 "부족한지 여부"라 과한 정밀도 |
| 화이트보드를 디지털로만 옮김(카운트만 기록) | 구현 간단 | 마지막으로 센 이후 시간이 지날수록 부정확해짐, "지금 뭐 만들어야 하나"에 실시간성이 없음 |
| **통 단위 카운트 + Square 판매량 자동 차감(채택)** | 세는 시간 최소(통 단위, 소수 허용), 카운트 사이에도 Square 실제 판매로 자동 갱신되어 실시간에 가까움 | 맛별 자동 차감이 되려면 Square가 맛을 기록해야 함(계산대 습관 필요, 오너가 장기적으로 개선하기로 결정) |

## 결정

**메커니즘**: `stock_events`에 두 종류만 기록한다.
- `count`: 지금 실제로 센 통 수 — **기준점을 리셋**한다(그 시점의 절대값)
- `production`: 방금 만든 통 수 — 기준점에 **더해진다**

현재 추정 재고 = (마지막 count 시점 통 수 + 그 이후 production 합) × 통당개수 − 그 이후 Square 실제 판매량. 다음 count가 오면 그 사이 안 잡힌 오차(폐기·서비스 등)가 자동으로 보정된다 — 별도 폐기 기록 기능은 만들지 않음(정밀도보다 실용성 우선, 오너 의도와 일치).

**상태 표시(5단계)**: 없음 / 거의없음 / 조금여유 / 보통 / 충분 — 남은 개수가 아니라 **최근 28일 평균 판매 속도 대비 며칠 버티는지**(`days_left`)로 계산. 같은 "1통 남음"이어도 잘 나가는 맛과 안 나가는 맛은 다르게 판단해야 하므로.

**입력**: Discord `/stock item:<품목명> containers:<통수, 소수 가능> type:<count|production>`. 이름은 `stock_items.name`에 ILIKE 부분일치, 모호하면 후보를 보여주고 재입력 요청.

**조회**: `/stock`은 기록 전용, 현재 상태 확인은 `/ask`(예: "마카롱 재고 어때", "지금 뭐 만들어야 돼")로 — `analytics_stock_overview`가 `stock_status` analysis로 Query Contract에 등록됨.

**맛별 데이터 정확도**: Square 주문 데이터를 실제로 까보니 마카롱은 78%, 쿠키는 63%가 맛 선택 없이 "Regular"로만 찍혀 있어 맛별 자동 차감이 안 됨. 오너 결정: 장기적으로 계산대에서 맛을 제대로 선택하는 걸로 개선(공사 진행 상황 아님, 습관 변화 — 시간이 지나며 데이터 품질 자연 개선).

## 스키마 (`db/migrations/0021`, `0022`)

- `stock_items(name, location_id, square_item_name, square_variation_name, units_per_container, container_label)` — 완제품 정의 + Square 매칭 키
- `stock_events(stock_item_id, event_type, container_count, occurred_at, created_by)` — count/production 이벤트만
- `analytics_stock_overview(p_location_id)` — 실시간 추정 재고+상태, Query Contract 등록(`stock_status`)

## 근거

- 폐기·서비스 별도 기록을 안 만든 이유: 다음 count가 자동으로 드리프트를 흡수하므로, 그 정밀도를 위해 매번 별도 기록을 강제하면 오너가 원래 피하고 싶어했던 "세는 부담"이 다시 생김
- 통 단위(소수 허용)로 한 이유: "1.5통" 같은 표현이 실제 생산·카운트 방식과 정확히 일치 — 개당 정밀 카운트보다 훨씬 빠름
- `/stock`과 `/ask`를 분리한 이유: 기록(빠른 입력, 고정 파라미터)과 조회(자연어, 여러 품목 종합)는 다른 인터랙션 패턴이 맞음
