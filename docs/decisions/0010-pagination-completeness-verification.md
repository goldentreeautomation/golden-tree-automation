# 0010. 전체 기간 페이지네이션 완전성 검증 (0001 버그 #9 해결)

- 날짜: 2026-08-25
- 상태: 채택

## 맥락

`docs/decisions/0001` 버그 #9(페이지네이션 누락)가 "검증 불가"(당시 Square API 권한 없음) → 이후 "하루치 표본(228건)만 확인, 전체 기간 미확인"으로 남아 있었다. M1 완료 기준이 "Square Dashboard와 센트 단위 일치"인데, 이 검증이 하루짜리 표본에 불과해 완전성을 보장하지 못했다.

## 방법

Square Orders Search API를 우리 동기화 코드와 동일한 커서 페이지네이션으로 전체 기간(2025-06-01~2026-08-26, 70,013건, 141페이지)에 대해 직접 재조회하고, 반환된 `order_id` 전체 집합을 우리 `orders` 테이블의 `square_order_id` 집합과 위치별로 diff했다.

## 결과

- **DB에만 있고 Square 조회에 없는 주문(20+3건)**: 전부 스크립트 실행 시점(2026-08-26T00:00 UTC) 직후에 생성된 최신 주문 — 조회 window의 끝 시각을 살짝 지난 것뿐인 타이밍 문제, 실제 데이터 문제 아님(Square 단건 조회로 `created_at`이 window 밖임을 확인).
- **Square엔 있는데 DB에 없는 주문(35건)**: **진짜 공백**. 전부 **2026-08-13 20:31:13~23:31:16 UTC(정확히 3시간)** 사이에 생성된 것으로 정확히 클러스터링됨 — CozyHaus 33건, Bon Sushi 2건. 시간별 동기화로 전환하기 전(구 방식: "마지막 성공 시점 − 48h"로 창을 밀어가는 로직)에 한 번의 실패/누락이 이후 영구히 재조회되지 않고 묻힌 것으로 추정(정확한 원인은 당시 로그가 없어 확정 못 함, 그러나 2026-08-25에 이미 "항상 지금−48h" 고정 방식으로 구조적으로 재발 방지함).

## 결정

`square-sync`에 `{"since":"2026-08-13T19:00:00Z","until":"2026-08-14T01:00:00Z"}`로 타겟 재동기화를 실행해 35건을 채웠다(idempotent upsert, 위험 없음 — G4 대상 아님. 데이터 "수정"이 아니라 정상 동기화 경로로 "추가"하는 것이라 기존 재동기화 승인 범위 안에 있다고 판단).

## 결과 (사후 기록)

35건 전부 DB에 정상 삽입 확인. 이제 이 시스템은 전체 기간(70,013건)에 대해 Square 원본과 주문 ID 단위로 대조를 마쳤고, 알려진 공백은 없다. 이후 재발 방지는 이미 2026-08-25 `square-sync`를 "항상 지금−48h 고정 창"으로 바꾼 것(hourly cron)이 구조적으로 담당한다 — 이 방식에선 이런 종류의 영구 누락이 원천적으로 불가능하다(매시간 항상 최근 48시간을 다시 훑으므로 한 번의 실패가 다음 실행에서 자동 복구됨).
