# Golden Tree — 통합 설계서

> 82 Bakeshop Ltd. 경영 데이터 · AI 에이전트 시스템
> 작성일 2026-08-23 · 버전 0.1 (초안)
> 이 문서는 Claude Code에서 구현할 때 참조하는 계획서다. 상세 구현 내용은 담지 않는다.

# 1부. 작업 컨텍스트

## 1.1 배경

82 Bakeshop Ltd.는 Regina에서 CozyHaus(디저트 카페)와 Bon Sushi(일식당) 두 매장을 운영한다. 월 매출 약 $140,000, 순이익률 약 15%. 2027년 겨울 Saskatoon 3호점을 목표로 하고 있다.

현재 경영 데이터가 여러 시스템에 흩어져 있다. Square에 매출, QuickBooks에 비용, Excel에 인건비, 종이 영수증에 구매 내역, Instagram에 마케팅 성과가 각각 존재하고, 현장 상황과 회의에서 내린 결정은 어디에도 기록되지 않는다. 그 결과 대부분의 운영 판단이 "요즘 좀 안 바쁜 것 같은데" 수준의 감각에서 출발한다.

### 선행 시도에서 확인된 실패 원인

n8n + Supabase로 Square 데이터를 수집하는 시도를 한 차례 진행했고, 데이터 수집 자체는 성공했으나 다음 문제로 중단했다. 이 설계서는 아래 세 가지를 구조적으로 해결하는 것을 전제로 한다.

| 실패 원인 | 결과 | 본 설계의 대응 |
|---|---|---|
| 상태가 저장되지 않음 | 세션이 끝나면 스키마 결정과 그 이유가 사라짐. 매번 처음부터 재설명 | 레포와 git이 회사의 기억. 결정은 `docs/decisions/`에 기록 |
| Query 계약 부재 | AI가 매번 SQL을 즉석에서 지어냄. 같은 질문에 다른 답 | DB 함수 목록을 계약으로 고정. 런타임 봇은 raw SQL 금지 |
| 시각적 도구 의존 | n8n 워크플로는 JSON 덩어리라 Claude Code가 읽고 고칠 수 없음 | 모든 로직을 코드로. Claude Code가 유지보수 주체 |

## 1.2 목적

두 가지다. 새 기능을 검토할 때 이 둘 중 하나에 해당하지 않으면 우선순위를 내린다.

1. **회사가 경험한 것을 잊지 않게 한다** — 매출, 결정, 결과, 가격 변동, 성공과 실패를 축적한다
2. **오너의 시간 투입을 줄인다** — 조회, 집계, 보고, 반복 입력을 자동화한다

2호점 이후에는 축적된 운영 기준을 신규 매장에 그대로 적용하고 비교하는 것이 최종 가치다.

## 1.5 제약조건

| 제약 | 설계 반영 |
|---|---|
| 오너가 코드를 직접 쓰지 않는다 | 모든 변경은 Claude Code와 자연어 대화로 수행 |
| 개발팀이 없다 | 유지보수 최소화 우선. 서비스 수를 늘리지 않는다 |
| 맥북에 의존하면 안 된다 | 서버리스. 실행 주체는 Supabase. 맥북은 개발 전용 |
| 실시간이 아니어도 된다 | 두 매장 모두 22:00 마감. 일 1회 배치로 충분 |
| 직원이 나중에 합류한다 | 모든 화면 모바일 우선. 인증은 나중에 붙이되 구조는 열어둠 |
| 런타임 비용 월 $20 이하 | Query Contract로 프롬프트 최소화. 저가 모델 사용 가능하게 |
| 세무·법률 판단은 자동화 금지 | 자료 생성까지만. 확정은 사람 |
| 두 매장을 항상 구분 | 모든 테이블·함수·화면에 location 차원 필수 |

## 1.6 용어 정의

| 용어 | 정의 |
|---|---|
| **Query Contract** | 런타임 봇이 호출할 수 있는 DB 함수의 고정 목록. 이 목록 밖의 데이터 접근은 금지된다 |
| **빌더 에이전트** | `.claude/agents/` 에 정의. Claude Code에서 실행되며 시스템을 만든다. 오너 책상에서만 동작 |
| **런타임 봇** | `runtime/personas/` 에 정의. Supabase에서 실행되며 Discord 질문에 답한다. 24시간 동작 |
| **Net Sales** | Gross Sales − Discount. 세금과 팁 제외. 모든 "매출" 표현의 기본값 |
| **business_date** | Regina 현지시각 기준 영업일. Square가 주는 UTC와 다르므로 반드시 변환해 저장 |
| **upsert** | 없으면 삽입, 있으면 갱신. 중복 없이 재실행 가능하게 하는 저장 방식 |
| **idempotent** | 같은 작업을 몇 번 반복해도 결과가 동일한 성질. 모든 동기화의 필수 조건 |
| **Edge Function** | Supabase에서 실행되는 서버리스 코드. 예약 또는 호출 시에만 깨어난다 |
| **승인 게이트** | 사람 승인 없이 통과할 수 없는 지점. 4개 정의 (3.7 참조) |
| **LOC_001 / LOC_002** | CozyHaus / Bon Sushi 내부 식별자. Square location_id와 매핑 |

## 1.7 레이어 구조와 Phase 배치

시스템은 4개 레이어로 구성된다. 새 기능은 아래 두 레이어에만 추가되고, 위 두 레이어는 거의 변경되지 않는다.

```
INTERFACE   Discord 봇  │  대시보드  │  정기 리포트
                  ↑ 전부 CONTRACT만 호출
CONTRACT    Query 함수 목록 — 시스템의 유일한 데이터 출입구
                  ↑
DATA        Supabase — 정규화 테이블 + 원본 JSONB
                  ↑
INGESTION   Square │ Meta │ Notion │ GSC │ GBP │ 영수증 │ QuickBooks
```

### 15개 Phase가 어느 레이어에 들어가는가

| Phase | 내용 | 주로 추가되는 레이어 | M |
|---|---|---|---|
| 1 | 통합 데이터베이스 | INGESTION + DATA | M1 |
| 2 | 매출 분석 엔진 | CONTRACT | M1 |
| 3 | Discord AI 비서 | INTERFACE | M2 |
| 4 | 정기 경영 리포트 | INTERFACE | M2 |
| 5 | 소셜미디어·광고 수집 | INGESTION | M2 |
| 6 | 광고와 매출 연결 | CONTRACT | M3 |
| 7 | 영수증 촬영·비용 입력 | INGESTION | M3 |
| 8 | 인보이스·이메일·매입 | INGESTION | M3 |
| 9 | 회계·세금 | INGESTION + CONTRACT | M4 |
| 10 | 원가·메뉴 수익성 | CONTRACT | M4 |
| 11 | 재고·발주 | DATA + CONTRACT | M4 |
| 12 | 직원·인건비·스케줄 | INGESTION + DATA | M4 |

추가로 발생한 순서 변경이 하나 있다. **웹사이트 개편보다 Search Console·GBP 연결이 먼저다.** 개편 전 기준선 데이터가 없으면 개편의 성패를 측정할 수 없고, URL 구조 변경으로 기존 순위를 잃어도 알 수 없다.

# 2부. 워크플로우 정의

## 2.0 판단과 코드의 역할 분리 (전역 원칙)

| 자연어 질문 → 호출할 함수 선택 | Square/Meta API 호출 |

## W1. 일일 데이터 동기화

### 흐름

```
22:00 스케줄 발화
  → sync_log에서 마지막 성공 시각 조회
  → 조회 시작점 = 마지막 성공 − 48시간
  → Square Orders 검색 (COMPLETED만, 페이지네이션)
  → 원본을 raw_square_orders에 upsert
  → 정규화 (시간대 변환, Net Sales 계산, 금액 단위 통일)
  → orders upsert  ─┐ 하나의 트랜잭션
  → order_items upsert ─┘
  → sync_log 기록
  → W3 검증 호출
  → W6 이상 감지 호출
```

### 설계 근거

- **48시간 소급**: Square 주문은 사후 수정될 수 있다. 마지막 동기화 이후만 가져오면 수정분을 놓친다. upsert이므로 중복 비용은 없다
- **COMPLETED만**: 진행 중 주문은 이후 변경된다. 마감 후 배치이므로 완료 주문만 다뤄도 손실이 없다
- **원본 별도 보관**: 6개월 뒤 modifier나 fulfillment를 분석하고 싶어질 때 Square API를 다시 뒤지지 않아도 된다
- **단일 트랜잭션**: orders만 저장되고 order_items가 실패하면 데이터가 깨진다. 둘을 하나의 DB 함수 안에서 처리한다

### 단계별 정의

| 단계 | 처리 | 성공 기준 | 검증 유형 | 실패 시 |
|---|---|---|---|---|
| 마지막 sync 조회 | 코드 | 값이 존재하거나 초기값 반환 | 스키마 | 초기값으로 진행 |
| Square 호출 | 코드 | HTTP 200, 페이지 전부 수신 | 규칙 기반 | 자동 재시도 3회(지수 백오프) → 실패 시 에스컬레이션 |
| 원본 저장 | 코드 | 수신 건수 = 저장 건수 | 규칙 기반 | 자동 재시도 1회 → 에스컬레이션 |
| 정규화 | 코드 | 필수 필드 전부 non-null, business_date가 Regina 기준 | 스키마 | 해당 건 스킵 + 로그, 나머지 진행 |
| upsert | 코드 | 트랜잭션 커밋, 재실행 시 행 수 불변 | 규칙 기반 | 롤백 후 에스컬레이션 |
| sync_log 기록 | 코드 | 행 1건 추가 | 스키마 | 에스컬레이션 |

### 재실행 안전성

동일 날짜로 3회 실행했을 때 `orders`와 `order_items`의 행 수가 변하지 않아야 한다. 이것이 W1의 인수 조건이다.

## W2. 과거 데이터 백필

### 흐름

```
시작일·종료일 입력
  → 일 단위로 분할
  → 각 날짜에 W1의 수집·정규화·저장 로직 재사용
  → 진행률 출력
  → 완료 후 전체 기간 W3 검증
```

### 정의

| 항목 | 내용 |
|---|---|
| 성공 기준 | 요청 기간의 모든 날짜에 대해 orders 행이 존재하고, 휴무일은 0건으로 명시적 기록 |
| 검증 유형 | 규칙 기반 (날짜 연속성) + W3 |
| 실패 시 | 날짜 단위 자동 재시도 2회 → 실패한 날짜 목록을 `/output/backfill_failures.json`에 기록 후 계속 진행 |
| 주의 | W1과 코드를 공유한다. 백필 전용 로직을 따로 만들지 않는다 |

## W3. 정확성 검증

M1의 완료를 판정하는 워크플로우다. "실행됨"이 아니라 "숫자가 맞음"이 완성 기준이다.

### 흐름

```

  → Supabase 집계 (주문 수, Net Sales, 세금, 팁, 상위 품목)
  → Square Reports API 또는 수동 입력값과 대조

| 항목 | 내용 |
|---|---|

날짜 | 항목 | Square | Supabase | 차이 | 판정
```

## W4. Discord 질문 응답

### 흐름

```
슬래시 명령 수신 (/ask, /sales, /items …)
  → 라우터: 질문 → Query Contract 함수 + 파라미터 결정   [LLM]
  → 계약에 없는 요청이면 → 안내 메시지 후 종료
  → DB 함수 실행                                        [코드]
  → 결과 → 자연어 답변 생성                              [LLM]
  → Discord 응답 (+ 사용한 함수명 표기)
```

### 슬래시 명령을 쓰는 이유

채널의 모든 메시지를 읽으려면 봇이 24시간 연결을 유지해야 하고, 그러면 서버가 필요해진다. 슬래시 명령은 호출 시에만 깨어나므로 서버리스로 동작한다. 부수 효과로 입력이 구조화되어 데이터 품질도 좋아진다.

### 정의

| 단계 | 처리 | 성공 기준 | 검증 유형 | 실패 시 |
|---|---|---|---|---|
| 함수 선택 | LLM | 계약 내 함수명 반환, 파라미터 타입 일치 | 스키마 | 재시도 1회 → 실패 시 "이 질문은 아직 답할 수 없습니다" + 질문을 `/output/unanswered.jsonl`에 기록 |
| 함수 실행 | 코드 | 정상 반환 | 스키마 | 에스컬레이션 |
| 답변 생성 | LLM | 조회 결과의 숫자만 사용. 없는 수치 생성 금지 | LLM 자기 검증 | 재시도 1회 → 원자료 그대로 출력 |

### 답변에 사용한 함수명을 붙이는 이유

숫자를 신뢰할 수 있는지 오너가 판단할 수 있어야 한다. 어떤 함수로 어떤 기간을 조회했는지 보이면 잘못된 답을 즉시 식별할 수 있다.

### `unanswered.jsonl`의 용도

답하지 못한 질문이 곧 다음에 만들 Query 함수의 목록이 된다. 계약을 추측이 아니라 실사용에 근거해 확장한다.

## W6. 이상 감지

오너가 선택한 알림 정책은 "정기 리포트 + 이상 감지"다. 능동 제안(예: 인원 조정 권고)은 데이터가 충분히 쌓인 뒤 M5에서 다룬다.

### 감지 대상

| 유형 | 조건 | 심각도 | 가용 시점 |
|---|---|---|---|
| 동기화 실패 | W1 실패 또는 sync_log 누락 | 높음 | M1 즉시 |
| 데이터 공백 | 영업일인데 orders 0건 | 높음 | M1 즉시 |
| 검증 불일치 | W3에서 차이 발생 | 높음 | M1 즉시 |
| 매출 급변 | 같은 요일 최근 4주 평균 대비 ±25% | 중간 | 데이터 4주 후 |
| 품목 이상 | 평소 판매되던 메뉴가 0건 (품절 의심) | 낮음 | 데이터 4주 후 |

### 정의

| 항목 | 내용 |
|---|---|
| 성공 기준 | 높음 등급 이상은 발생 후 10분 내 Discord 알림 |
| 검증 유형 | 규칙 기반 (임계값). 원인 후보 추론만 LLM |
| 실패 시 | 알림 전송 실패 시 재시도 3회 → 대시보드 배너로 대체 표시 |
| 임계값 관리 | 하드코딩 금지. `thresholds` 테이블에 두고 대시보드에서 조정 |

### 4주 유예 이유

기준선 없이 임계값을 정하면 오탐이 쏟아진다. 오탐이 반복되면 알림을 무시하게 되고, 그 시점에 시스템은 실패한 것이다. 처음 4주는 수집만 하고 5주차부터 임계값을 켠다.

## W8. 승인 게이트

오너가 4개 게이트를 모두 선택했다. 자동 실행하지 않고 반드시 사람을 거친다.

| ID | 게이트 | 대상 작업 | 승인 위치 | 가용 |
|---|---|---|---|---|
| G1 | 외부 공개 콘텐츠 | 블로그 발행, Google 리뷰 답글, GBP 게시물, 소셜 포스팅 | 대시보드 (미리보기 필요) | M3 |
| G2 | 지출 | 발주, 지불, 광고 예산 집행 | Discord (즉시성 필요) | M3 |
| G3 | 회계·세금 확정 | 비용 분류 확정, QuickBooks 전송, GST/PST 신고 자료 | 대시보드 | M4 |
| G4 | DB 구조 변경 | 마이그레이션 실행, 데이터 일괄 수정·삭제 | Claude Code 대화 중 명시적 확인 | **M1** |

G1~G3은 해당 작업을 수행하는 워크플로우가 생기는 시점(M3 이후)에 활성화된다. **M1에서 실제로 작동해야 하는 것은 G4뿐이다.** 다만 승인 흐름과 폴더 구조는 처음부터 공통으로 만들어 두어, 나중에 게이트를 추가할 때 구조를 다시 짜지 않는다.

### 공통 흐름

```
에이전트가 결과물 생성
  → /output/pending/{gate}/{id}.json 저장
  → 승인 요청 전송 (게이트별 위치)
  → 승인 / 반려 / 수정 요청
  → 승인 시에만 실제 실행
  → /output/approved/ 로 이동, 이력 보존
```

### 정의

| 항목 | 내용 |
|---|---|
| 성공 기준 | 승인 없이 실행된 게이트 대상 작업이 0건 |
| 검증 유형 | 사람 검토 |
| 실패 시 | 24시간 무응답 시 알림 1회 재발송. 자동 승인은 어떤 경우에도 없다 |

### G4가 별도로 존재하는 이유

선행 시도에서 대화 도중 `TRUNCATE`가 실행되어 수집한 데이터가 삭제된 사례가 있었다. 빌더 에이전트는 마이그레이션 파일을 **작성**할 수 있으나, 운영 DB에 **실행**하려면 별도 확인을 거친다.

# 3부. 구현 스펙

> 구조와 역할 정의까지만 기술한다. 각 파일의 본문은 구현 시 작성한다.

## 3.1 에이전트 두 종류 — 혼동 금지

이 시스템에는 성격이 완전히 다른 두 종류의 에이전트가 존재한다. 문서와 코드 전반에서 구분해 부른다.

| | 빌더 에이전트 | 런타임 봇 |
|---|---|---|
| 위치 | `.claude/agents/` | `runtime/personas/` |
| 실행 환경 | Claude Code (오너 맥북) | Supabase Edge Function (클라우드) |
| 실행 시점 | 개발할 때만 | 24시간 |
| 대화 상대 | 오너 (VS Code 안에서) | 오너·사촌동생 (Discord에서) |
| 하는 일 | 코드와 스키마를 만든다 | 데이터를 조회해 답한다 |
| 권한 | 레포 전체 쓰기, DB 실행은 G4 통과 필요 | Query Contract 읽기 전용 |
| 비용 | 오너의 Claude 구독 | 호출당 과금 (월 $2~15) |

`.claude/agents/`에 런타임 봇을 정의하면 안 된다. 실행 환경이 다르다.

## 3.4 빌더 에이전트

**서브에이전트로 분리하는 근거**: 네 영역이 각각 다른 도메인 지식(SQL/Postgres, 외부 API 스펙, React/CSS, 회계 검증 규칙)을 요구하며, 지침을 항상 로드하면 컨텍스트 낭비가 크다. 필요한 시점에만 로드한다.

메인(CLAUDE.md)이 오케스트레이터다. **서브에이전트끼리 직접 호출하지 않는다.**

| 이름 | 역할 | 트리거 | 입력 | 출력 |
|---|---|---|---|---|
| `db-architect` | 스키마, 마이그레이션, Query 함수 | 테이블·컬럼·함수 관련 요청 | 요구사항, 기존 스키마 | `db/migrations/*.sql`, `db/functions/*.sql`, 계약 명세 갱신 |
| `integration-builder` | 외부 API 연동 | 새 데이터 소스 추가, 동기화 수정 | API 문서, 대상 테이블 | `sync/{source}/*`, 스케줄 설정 |
| `frontend-builder` | 대시보드 페이지 | 화면 추가·수정 | 사용할 Query 함수, 화면 요구 | `web/app/**` |
| `verifier` | 정확성 검증 | 동기화 후, 마일스톤 판정 시 | 대상 기간 | `output/verification/*.json`, 합격·불합격 판정 |

### 데이터 전달

파일 기반을 원칙으로 한다. 중간 산출물은 `/output/`에 저장하고 경로만 전달한다. 검증 결과, 스키마 스냅샷처럼 구조화되고 양이 많은 데이터가 대부분이기 때문이다. 단일 값(날짜, 매장 ID 등)만 프롬프트 인라인으로 전달한다.

## 3.5 스킬

**스킬과 서브에이전트의 구분**: 스킬은 도구 단위이며 여러 에이전트가 공유한다. 서브에이전트는 역할 단위다.

| 스킬 | 역할 | 트리거 조건 | 주 사용자 |
|---|---|---|---|
| `verify-sync` | Supabase 집계와 Square 값 대조, 차이 리포트 생성 | W1 완료 후 / "숫자 맞는지 확인" 요청 시 / 마일스톤 판정 시 | verifier |
| `add-connector` | 새 데이터 소스 연동 골격 생성 (인증, 페이지네이션, 재시도, upsert 패턴) | "○○ 연결하고 싶다" 요청 시 | integration-builder |
| `add-query-function` | Query 함수 생성 + 계약 명세 등록 + 라우터 갱신을 한 번에 | 새 조회 요구 발생 시 / `unanswered.jsonl` 검토 시 | db-architect |
| `add-dashboard-page` | 모바일 우선 페이지 골격 생성, 기존 Query 함수에 연결 | "○○ 화면 만들어줘" 요청 시 | frontend-builder |
| `run-migration` | G4 승인 절차 수행 후 마이그레이션 실행, 롤백 스크립트 동시 생성 | 마이그레이션 실행 요청 시 (항상 G4 경유) | db-architect |

`add-query-function`이 세 가지를 묶는 이유는 이 셋이 어긋나면 즉시 장애가 나기 때문이다. 함수는 있는데 계약에 없으면 봇이 못 부르고, 계약에 있는데 함수가 없으면 봇이 오류를 낸다.

## 3.6 런타임 봇

Discord 채널이 곧 봇의 방이다. 각 방은 자기 주제의 문맥과 접근 가능한 함수 범위를 유지한다.

| 봇 | 채널 | 담당 | 접근 범위 | M |
|---|---|---|---|---|
| `analyst` | `#analyst` | 매출, 상품, 시간대, 매장 비교 | 매출 계열 함수 | M2 |
| `marketing` | `#marketing` | 소셜 성과, 광고 효과 | 마케팅 + 매출 함수 | M2 |
| `seo` | `#seo` | 검색 노출, 리뷰, GBP | 검색 함수 | M3 |
| `bookkeeper` | `#bookkeeper` | 비용, 영수증, 세금 자료 | 비용 함수 | M3 |
| `chief` | `#office` | 다른 봇에게 질의 후 종합 | 전체 (읽기) | M3 |

### `chief`의 성격

에이전트끼리 잡담하는 구조가 아니다. 오너의 광범위한 질문(예: "이번 주 먼저 해결할 문제 3개")을 받아 필요한 봇에게 질의하고 답을 취합하는 **오케스트레이터**다. 봇끼리의 자율 대화는 비용과 불확실성만 늘리므로 만들지 않는다.

### persona 정의에 담을 항목

역할, 담당 영역, 호출 가능한 함수 목록, 답변 톤, 모르는 것을 물었을 때의 행동, 승인 게이트 해당 여부.

## 3.7 Query Contract

시스템의 중심 산출물이다. 명세는 `docs/contracts/`에 두고, 함수 추가 시 반드시 함께 갱신한다.

### 규칙

1. 런타임 봇은 계약에 등재된 함수만 호출한다. raw SQL 금지
2. 모든 함수는 읽기 전용
3. 모든 함수는 `location` 파라미터를 받는다 (전체 조회 시 null)
4. 금액 반환 단위와 세금·팁 포함 여부를 함수마다 명시한다
5. 함수 추가 시 계약 명세와 라우터를 동시에 갱신한다 (`add-query-function` 스킬이 강제)

### M1 초기 함수

| 함수 | 용도 |
|---|---|
| `get_sales_summary` | 기간·매장별 Net Sales, 주문 수, 객단가 |
| `get_sales_by_hour` | 시간대별 매출·주문 수 |
| `get_top_items` | 기간·매장별 판매 상위 품목 |
| `get_item_sales` | 특정 품목의 기간별 판매 추이 |
| `get_sync_status` | 최근 동기화 이력과 검증 결과 |

이후 함수는 `unanswered.jsonl`에 쌓인 실제 질문을 근거로 추가한다. 미리 상상해서 만들지 않는다.

## 3.8 주요 산출물 형식

| 산출물 | 위치 | 형식 |

| 장애 대응 | `docs/runbooks/` | `.md` |
